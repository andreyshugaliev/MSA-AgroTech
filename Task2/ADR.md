### <a name="_qmphm5d6rvi3"></a>**Решение**
1. Микросервис управления. Сразу обрабатывает данные с датчиков и отсылает команды, поскольку если разделить на два микросервиса, между ними будет слишком большая связанность и один всегда будет управлять вторым.
2. Обмен данными идёт через шину RabbitMQ, выбрана из-за простоты понимания, предполагаемых небольших объёмах (одна ферма) и наличии Dead Letter Queue, что важно при сбоях в работе Wi-Fi.
3. Хранит кэш в Redis, поскольку данные о кормах на складе и кол-ве животных не требуют обновления в реальном времени.
4. Внешнее api. Авторизация через Keycloak и обмен данными через RESTful API: легковесно и достаточно для веб- и мобильных приложений.
5. БД на PostgreSQL поскольку никаких специфических требований к БД не было.
6. Микросервис анализа данных с камер, тоже работает через RabbitMQ, т.к. обработанный нейросетью тяжёлый видеопоток превращается в небольшого объёма данные.


Для обеспечения быстрой реакции видеоаналитики, видеопоток непосредсвенно идёт на нейросеть.
### <a name="_bjrr7veeh80c"></a>**Альтернативы**
Альтернативой является добавление сервиса фильтрации видео, он работает с помощью gRPC из-за большого объёма даже отфильтрованных данных.
**Недостатки, ограничения, риски**

1. Высокая связанность сервиса обработки данных с камер и сервиса оповещения персонала
2. Проблемное масштабирование сервиса управления
3. Передача данных для синхронизации через API возможно даст большую нагрузку.
